# 하네스, 오케스트레이션, 에이전트 역할 지도

작성일: 2026-06-24  
대상 프로젝트: 전기기사 5,331문제 study display-ready / figure lane / answer trust / sidecar preview 자동화  
연결 문서:
- `docs/research/study_display_3307_architecture_decision_record_v2_20260624.md`
- `docs/research/llm_architecture_loop_prevention_report_20260624.md`

## 한 줄 결론

우리 프로젝트는 "에이전트가 알아서 해결한 프로젝트"가 아니라, **LLM을 작업자로 쓰되 하네스와 guard가 권한을 잡는 프로젝트**였다. 에이전트는 넓게 생각하고 움직였고, 오케스트레이션은 작업 순서를 짰고, 하네스는 결과를 붙잡아 검증했으며, 아키텍처는 누가 어떤 권한을 갖는지 정했다.

## 1. 용어를 먼저 정리한다

### 1.1 하네스 엔지니어링

하네스는 원래 시험 장치, 묶어 두는 장치, 안전띠에 가까운 말이다. 소프트웨어와 LLM 프로젝트에서는 다음 역할을 한다.

- 모델이나 코드가 마음대로 성공을 선언하지 못하게 한다.
- 입력과 출력의 형태를 고정한다.
- count, schema, parse, render, hash, file existence 같은 닫힌 검사를 한다.
- 실패하면 어디에서 실패했는지 드러낸다.
- 다음 LLM이나 다음 세션이 같은 결과를 재현하게 한다.

우리 프로젝트에서 하네스는 사실상 가장 중요한 구조였다. LLM이 "됐습니다"라고 말하는 대신, 하네스가 "이 파일이 있고, 이 숫자가 맞고, 이 guard가 통과했다"고 말하게 했다.

### 1.2 하메스 엔지니어링

사용자가 말한 "하메스"가 "하네스"의 오기라면 같은 의미로 보면 된다. 만약 별도 용어로 쓴다면, 우리 프로젝트에서는 독립 개념으로 자리 잡지는 않았다. 우리가 실제로 만든 것은 거의 전부 harness 성격이다.

이 문서에서는 "하네스"를 다음 뜻으로 고정한다.

> LLM, 코드, 데이터, 사람이 만든 결과가 목표에서 벗어나지 않도록 붙잡고 측정하는 장치.

### 1.3 오케스트레이션

오케스트레이션은 여러 작업자와 도구를 어떤 순서로 돌릴지 정하는 일이다.

우리 프로젝트에서는 이런 흐름이었다.

1. 전체 5,331개를 측정한다.
2. damaged/excluded를 분리한다.
3. answer trust를 계산한다.
4. figure/SVG lane을 따로 본다.
5. display-ready와 meaning-ok를 분리한다.
6. SVG parse/render/mobile 검사를 돌린다.
7. text-only practice lane을 만든다.
8. 남은 hold를 다시 작은 원인군으로 쪼갠다.
9. 사람이 볼 항목을 최소화한다.
10. 모든 단계마다 guard와 자연어 기록을 남긴다.

오케스트레이션은 작업 순서의 지휘자다. 하지만 지휘자는 심판이 아니다. 심판은 하네스와 guard여야 한다.

### 1.4 에이전트

에이전트는 목표를 받고 도구를 써서 행동하는 작업자다. Codex, Claude, 또는 여러 렌즈 역할을 맡은 LLM이 여기에 해당한다.

우리 프로젝트에서 에이전트가 잘한 일은 다음이다.

- 실패 유형 후보를 넓게 펼쳤다.
- 다음 배치를 설계했다.
- 사람이 이해할 수 있는 보고서를 썼다.
- guard를 제안했다.
- 여러 파일과 결과를 읽고 다음 진행을 골랐다.

하지만 에이전트가 해서는 안 되는 일도 분명했다.

- 정답 의미 승인
- 그림 의미 승인
- 깨진 수식 임의 복원
- source 없는 사실 판정
- 원본 app data 직접 수정

에이전트는 작업자이지 최종 승인자가 아니다.

### 1.5 아키텍처

아키텍처는 단순히 폴더 구조나 코드 구조가 아니다. 이 프로젝트에서 아키텍처는 **권한 구조**였다.

- 무엇을 LLM에게 맡길 것인가?
- 무엇을 코드로 닫을 것인가?
- 무엇을 사람이 볼 것인가?
- 무엇을 원본 데이터에 반영하지 말고 sidecar로 둘 것인가?
- 어떤 결과는 display-ready이고, 어떤 결과는 meaning-ok가 아닌가?

아키텍처가 늦게 잡히면 LLM은 열심히 일하지만, 사용자는 무엇이 진전인지 알 수 없다. 이 프로젝트의 초반 무한 루프는 대부분 아키텍처 부재에서 왔다.

## 2. 우리 프로젝트의 실제 레이어를 다시 이름 붙이면

| 우리가 만든 것 | 일반적인 역할 이름 | 실제 역할 |
|---|---|---|
| answer trust | labeled ground-truth harness | 라벨링된 정답지를 기준으로 정답 lane을 닫음 |
| figure flags | visual-risk lens | 그림이 있는 문제의 위험 신호를 분리 |
| SVG parse check | syntax harness | SVG가 XML로 파싱되는지 확인 |
| browser render probe | render harness | 실제 브라우저에서 비어 있지 않게 보이는지 확인 |
| mobile smoke | device/display harness | 모바일에서 읽히는지 확인 |
| qid hygiene | identity reconciliation harness | row index, qid, 회차 표기, 중복 문제 연결 검증 |
| source locator | provenance/RAG lens | PDF/page/source anchor가 있는지 추적 |
| damaged/excluded lane | quarantine layer | 손상 데이터가 본류에 섞이지 않게 격리 |
| sidecar preview | safety adapter layer | 원본 app data 수정 없이 표시 후보를 붙임 |
| multi-lens triage | non-authoritative ensemble triage | 여러 렌즈가 위험을 찾되 최종 승인권은 갖지 않음 |
| final guard runner | one-command harness | 전체 상태를 한 명령으로 다시 확인 |
| decision record | architecture memory | 왜 그런 선택을 했는지 사람이 읽게 보존 |
| human cap 3 | human-in-the-loop compression gate | 사람이 볼 항목을 감당 가능한 수준으로 압축 |

이 표가 중요하다. 우리가 만든 많은 산출물은 이름은 제각각이지만, 대부분은 "LLM의 자유도를 줄이고 결과를 측정 가능하게 만드는 장치"였다.

## 3. 우리 프로젝트에서 하네스가 맡은 일

### 3.1 숫자를 닫았다

LLM이 "많이 처리했습니다"라고 말하는 것은 의미가 없다. 숫자는 코드가 닫아야 한다.

우리 프로젝트에서 하네스는 다음 숫자를 닫았다.

- 전체 5,331개
- 학습 대상 4,433개
- display-ready 3,307개
- remaining hold 47개
- page crop 후보 19개
- PDF-only render prep 2개
- external source request 1개

숫자가 닫히자 사용자는 "진짜 어디까지 왔는지" 볼 수 있었다.

### 3.2 의미 승인과 표시 가능성을 분리했다

초기에는 "좋은 공부 자료"라는 목표가 너무 컸다. 이 목표 안에는 여러 층이 섞여 있었다.

- 문제가 보이는가?
- 정답이 있는가?
- 해설이 있는가?
- 그림이 깨지지 않는가?
- 그림 의미가 정확한가?
- 수식이 원문과 일치하는가?

이 모든 것을 한 번에 승인하려 하면 끝나지 않는다. 그래서 하네스는 `display-ready`와 `meaning-ok`를 분리했다.

이 선택 덕분에 우리는 3,307개를 "시험 공부 화면에서 볼 수 있는 상태"로 닫을 수 있었다. 의미 완전 승인은 별도 문제로 남겼다.

### 3.3 원본 데이터를 보호했다

LLM이 원본 app data를 직접 고치게 하면 위험하다. 특히 깨진 수식, 잘린 SVG, source 없는 복원은 잘못 고치면 나중에 원인을 추적하기 어렵다.

그래서 sidecar preview를 만들었다.

- 원본 app data는 보존한다.
- 표시 후보는 sidecar로 붙인다.
- guard가 통과한 것만 preview한다.
- 의미 승인은 자동으로 하지 않는다.

이 구조는 하네스의 좋은 예다. LLM이 만든 결과를 바로 본류에 넣지 않고, 안전한 바깥 레이어에서 검증하게 했다.

### 3.4 사람이 볼 일을 줄였다

사람이 500개, 1,500개, 2,000개를 같은 텐션으로 보는 것은 불가능하다. 그래서 하네스는 사람이 볼 대상을 줄이는 데 집중했다.

중요한 것은 "사람을 빼는 것"이 아니라 "사람이 봐야 할 것만 남기는 것"이었다.

- 기계가 닫을 수 있는 것은 기계가 닫는다.
- LLM이 후보를 찾는다.
- guard가 통과/실패를 나눈다.
- source가 없거나 의미 판단이 필요한 것만 사람에게 보낸다.

이것이 human-in-the-loop의 현실적인 형태였다.

## 4. 오케스트레이션이 맡은 일

오케스트레이션은 하네스들을 어떤 순서로 돌릴지 정했다.

우리 프로젝트에서 좋은 오케스트레이션은 다음 순서를 지켰다.

1. 먼저 현재 상태를 측정한다.
2. 이미 닫힌 것을 다시 열지 않는다.
3. 남은 것을 원인별로 나눈다.
4. 가장 닫기 쉬운 것부터 닫는다.
5. 원본 데이터 수정은 마지막까지 미룬다.
6. 새 산출물에는 항상 guard를 붙인다.
7. 자연어 결정 기록을 남긴다.

이 순서가 없을 때 프로젝트는 옆길로 샜다. 이 순서가 생긴 뒤에는 "다음 안전 작업"이 가능해졌다.

## 5. 에이전트가 맡은 일

에이전트는 다음 일을 맡으면 좋다.

### 5.1 후보 생성

예를 들어 "왜 47개가 남았는가"를 물으면 에이전트는 여러 원인 후보를 제안할 수 있다.

- duplicate solution text
- text corruption
- source visual/manual
- SVG parse fail
- PDF-only
- no-local-anchor

이것은 에이전트가 잘한다. 그러나 후보 생성은 닫힌 결론이 아니다. 이후 코드 분류가 따라야 한다.

### 5.2 문서화

에이전트는 사람이 읽을 수 있는 문서를 잘 만든다.

- 아키텍처 결정 기록
- 무한 루프 방지 리포트
- 사용자 복귀 대시보드
- 다음 작업 순서
- 실패 원인 회고

이 능력은 매우 중요하다. 비개발자는 코드 diff만으로 프로젝트를 이해하기 어렵기 때문이다.

### 5.3 도구 호출 순서 제안

에이전트는 다음 guard를 어떤 순서로 돌릴지 제안할 수 있다. 하지만 제안한 순서는 실제 실행과 로그로 확인되어야 한다.

## 6. 우리 프로젝트에 맞지 않았던 접근

### 6.1 LLM 단독 승인

"LLM에게 보고 맞는지 판단하게 하자"는 방식은 우리 프로젝트에 맞지 않았다.

이유는 다음이다.

- 정답 의미는 라벨링된 정답지가 더 강한 기준이다.
- 그림 의미는 vision LLM도 hallucination 가능성이 있다.
- 깨진 수식은 그럴듯하게 복원될 수 있다.
- LLM judge는 편향이 있다.

그래서 LLM은 승인자가 아니라 보조자여야 했다.

### 6.2 다수결 LLM

여러 LLM이 같은 말을 하면 신뢰가 올라갈 수는 있다. 하지만 닫힌 진실이 되지는 않는다. 같은 source를 보지 못하거나 같은 편향을 공유하면 함께 틀릴 수 있다.

다수결은 위험 신호를 찾는 데는 쓸 수 있지만, 최종 승인은 guard와 source가 해야 한다.

### 6.3 전체 의미 완전 승인

5,331개 전체에 대해 그림 의미, 해설 의미, 정답 의미를 모두 완전 승인하려는 방식은 현실적인 ROI가 나오지 않는다.

그래서 우리는 목표를 나눴다.

- 먼저 display-ready를 만든다.
- 의미 위험은 따로 보류한다.
- 사람이 볼 것은 극소수로 줄인다.

이것이 시험 공부라는 실제 목표에 더 맞았다.

## 7. 하네스, 오케스트레이션, 에이전트의 관계

세 개를 사람 조직에 비유하면 다음과 같다.

- 아키텍처: 헌법
- 하네스: 감사팀과 계측기
- 오케스트레이션: 프로젝트 매니저
- 에이전트: 실제 작업자
- 사람: 최종 목표와 위험 허용치를 정하는 owner

작업자가 많아도 헌법과 감사팀이 없으면 일이 무한 루프에 빠진다. 반대로 하네스만 있고 에이전트가 없으면 탐색 속도가 느리다. 둘 다 필요하지만 권한은 다르게 배치해야 한다.

우리 프로젝트의 최종 권한 구조는 다음이 맞다.

1. 사용자가 목표와 위험 기준을 정한다.
2. 아키텍처가 권한 경계를 정한다.
3. 에이전트가 후보를 만들고 작업한다.
4. 오케스트레이션이 순서를 정한다.
5. 하네스가 결과를 닫는다.
6. 사람이 정말 필요한 작은 부분만 본다.

## 8. 다음 프로젝트에 가져갈 원칙

다음에 비슷한 프로젝트를 시작한다면 처음부터 다음을 만든다.

1. 목표 계약서
   - 무엇이 성공인지 자연어로 쓴다.

2. 권한 경계 문서
   - LLM이 해도 되는 일과 하면 안 되는 일을 쓴다.

3. 닫힌 지표 파일
   - count, pass, fail, hold, excluded를 JSON으로 둔다.

4. 하네스 runner
   - 모든 guard를 한 번에 돌린다.

5. source/provenance manifest
   - 어떤 원자료를 근거로 했는지 남긴다.

6. sidecar 우선 정책
   - 원본 데이터 수정 전에 preview로 검증한다.

7. human cap
   - 사람이 볼 최대 개수를 미리 정한다.

8. decision record
   - 왜 이 선택을 했는지 자연어로 남긴다.

이 8개가 있으면 LLM은 강력한 작업자가 된다. 이 8개가 없으면 LLM은 열심히 움직이지만 사용자는 프로젝트 내부를 볼 수 없다.

## 9. 이 문서의 최종 판정

우리 프로젝트에서 가장 중요한 것은 에이전트가 아니었다. 가장 중요한 것은 하네스였다.

하지만 하네스만으로도 충분하지 않았다. 하네스가 닫을 대상을 정하려면 아키텍처가 필요했고, 많은 하네스를 순서대로 돌리려면 오케스트레이션이 필요했고, 넓은 실패 후보를 찾으려면 에이전트가 필요했다.

따라서 우리 프로젝트의 정체성은 다음이다.

> 하네스 중심 LLM 오케스트레이션.

이 말이 가장 정확하다. LLM은 중요했다. 그러나 LLM이 왕은 아니었다. 왕은 목표, source, guard, 그리고 사용자가 감당 가능한 검수량이었다.
