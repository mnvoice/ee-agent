# 감독자 판단 근거 추론 로그 — T3.5 / G5 / H1

> 이 문서는 *작업 결과*가 아니라 *판단 과정과 고민*을 보존하기 위한 운영 일지다.
> 결과 기록은 `docs/audit/t3_5_regeneration_decision_log.md`에 있고, 이 문서는 그 결과에
> 도달하기까지 무엇을 망설였고 왜 그렇게 정했는지를 남긴다. 각 절은 나중에 JSONL
> decision dataset의 한 레코드로 구조화할 수 있도록 독립적으로 끊어 두었다.

---

## 1. 왜 repo decision log만으로는 부족한가

`t3_5_regeneration_decision_log.md`는 결과 중심이다. "T3.5-J G5 = CLOSED/PASS",
"Batch 1 19/19 PASS" 같은 *확정된 사실*은 잘 남지만, 그 사실에 이르기까지의 *분기점*은
남지 않는다. 예컨대 "표본 6건만 검증하고 끝낼 수도 있었는데 왜 74건 전수로 갔는가",
"Codex 브라우저가 구해설을 보여줬을 때 데이터를 의심하지 않은 이유는 무엇인가" 같은
질문에 결과 로그는 답하지 못한다.

결과 로그는 *무엇을 했는가*를 보존하고, 판단은 *왜 그렇게 했는가*에 있다. 후자가
유실되면 다음 cycle에서 같은 고민을 처음부터 다시 하게 되고, 더 나쁘게는 과거의
결론만 보고 그 전제가 바뀐 줄 모른 채 답습하게 된다.

## 2. 왜 Obsidian / 별도 supervisor log가 필요한가

판단 근거는 대화 중에 흩어진다. 채널 대화 원문은 자동 보존되지 않으므로, 세션이
끝나면 "그때 왜 그렇게 정했지"가 통째로 사라진다. repo decision log에 근거까지
욱여넣으면 결과 기록이 장황해지고, 반대로 안 넣으면 영영 잃는다.

그래서 결과(repo decision log)와 근거(supervisor reasoning log)를 *물리적으로 분리*
하되 짝으로 운용한다. Obsidian-ready Markdown으로 두는 이유는, 판단 근거는 사람이
검색·연결·재독하는 지식이기 때문이다. Obsidian의 태그·백링크가 cycle 간 판단을
이어 붙이는 데 맞다.

## 3. "결과 로그"와 "판단 근거 로그"의 차이

| 축 | 결과 로그 | 판단 근거 로그 |
|---|---|---|
| 보존 대상 | 확정 사실, 수치, 게이트 상태 | 분기점, 망설임, 기각한 대안, 전제 |
| 질문 | "무엇을 했는가" | "왜 그렇게 했는가" |
| 독자 | 감사·재현 | 다음 판단자(미래의 우리) |
| 변질 위험 | 낮음 (사실은 안 바뀜) | 전제가 바뀌면 결론도 재검토 필요 |
| 위치 | `docs/audit/*_decision_log.md` | `docs/audit/supervisor_logs/` |

핵심: 결과 로그는 *동결된 진실*, 판단 근거 로그는 *조건부 진실*이다. 후자는 "이
전제 하에서 이렇게 판단했다"를 남기므로, 전제가 바뀌면 재판단의 출발점이 된다.

## 4. clean Chrome / gstack 기준을 채택한 판단

G5는 "재생성 해설이 앱에서 정상 표시되는가"를 묻는다. 그런데 브라우저가 여럿이었다 —
gstack headless, Codex in-app browser. 같은 데이터라도 브라우저 캐시 상태에 따라
다른 화면이 나온다. 그러면 무엇을 *기준*으로 삼을지부터 정해야 했다.

선택은 "캐시 영향이 0인 컨텍스트"였다. 서비스워커 unregister + caches 삭제 + reload를
매 batch 선행한 clean Chrome을 고정 기준으로 박았다. 이유는 단순하다: 측정하려는 것이
*데이터·렌더의 정확성*인데, 캐시가 끼면 측정 대상이 오염된다. 기준을 흐리게 두면
"적당히 맞다"가 되고, 기준을 정밀하게 두면 "이 조건에서 분명히 맞다"가 된다. G5처럼
74건의 무결성을 보증하는 게이트는 후자여야 한다.

## 5. Codex in-app browser stale을 데이터 문제가 아니라고 분리한 판단

Codex 브라우저가 일부 항목에서 *재생성 이전*의 구해설을 보여줬다. 여기서 흔한 함정은
"표시가 틀렸으니 데이터를 의심하자"로 직행하는 것이다. 그러나 표시 오류의 원인은
데이터일 수도, 렌더일 수도, *환경*일 수도 있다.

세 가지 독립 근거가 환경(캐시)을 가리켰다: ① 앱이 서비스워커(`app/sw.js`)를 가지고
있어 stale 캐시가 구조적으로 가능하다, ② 정적 hash 검사 74/74가 `questions.json`·
`questions.v2.json`에 재생성 내용이 실제로 적재됨을 확인했다, ③ clean Chrome은 같은
데이터로 신해설을 정상 렌더했다. 데이터가 정상임이 ②로 증명된 이상, Codex의 구해설
표시는 데이터 결함이 아니라 그 브라우저 컨텍스트의 캐시 stale이다.

그래서 Codex 결과를 *판정 기준에서 제외*하고 참고용으로만 두었다. 이건 Codex를
무시한 게 아니라, 한 측정값의 *출처를 분리*해 오염원을 격리한 것이다.

## 6. 유료 API를 쓰지 않은 판단

이번 cycle의 작업 — G5 검증, hold 조사, figure crop — 은 전부 *결정적
(deterministic)* 이다. hash 비교, 렌더 게이팅 로직 복제, PDF 페이지 crop은 같은
입력에 같은 출력을 낸다. 여기에 LLM 추론을 끼우면 비용만 들 뿐 정확도는 오히려
불확정해진다.

판단 규칙은 "추론이 필요한가"였다. 검증·crop은 추론이 아니라 측정이므로 무 API.
반대로 hold 3건의 그림 의존 해설 *재생성*은 그림을 실제로 읽고 풀이를 써야 하므로
멀티모달 추론이 불가피하다 — 그래서 그것만 H2로 분리하고 별도 예산 승인 대상으로
남겼다. "API를 쓰지 않는다"가 아니라 "추론이 필요한 곳에만 쓴다"가 정확한 판단이다.

## 7. Claude CLI / 웹 Claude / 감독자 역할 분리 판단

검증의 신뢰성은 *누가 검증했는가*에 달려 있다. 작업을 실행한 주체가 자기 결과를
스스로 합격 판정하면 그건 검증이 아니라 자기 보증이다.

그래서 세 역할을 분리했다: Claude CLI는 실행과 1차 검증, 웹 Claude는 같은 대상에
대한 독립 판정, 감독자는 최종 승인과 commit 게이트. 빌더와 감사자를 나누는 원칙의
적용이다. Batch마다 "CLI 19/19 PASS / 웹 Claude 19/19 PASS / 감독자 승인"을 모두
기록한 것은, 한 채널의 착오가 다른 채널에서 걸리도록 하는 구조를 명시적으로 남기기
위해서다.

## 8. index.lock 충돌을 위험한 충돌이 아니라 운영 신호로 본 판단

commit 중 `.git/index.lock` 충돌이 두 번 났다. 반사적 대응은 "lock 파일을 지우고
진행"이다. 그러나 lock을 강제 삭제하는 것은, 다른 git 프로세스가 실제로 인덱스를
쓰는 중이라면 인덱스를 손상시킨다.

그래서 먼저 *조사*했다 — 활성 git 프로세스가 있는가, lock이 아직 있는가. 두 번 다
프로세스는 없었고 lock은 이미 자체 해제되어 있었다. 즉 일시적 race였고, 재시도로
정상 commit됐다.

여기서 한 걸음 더 나간 해석: 이 충돌은 *제거할 버그*가 아니라 *읽을 신호*다. 같은
repo를 병렬 프로세스(웹 Claude / Codex 등 멀티에이전트 구성)가 건드리고 있다는
방증이다. 위험한 충돌로 취급해 강제 해소했다면 그 신호를 지웠을 것이다. 운영 신호로
보면 "이 repo는 다중 작업자 환경"이라는 사실이 기록에 남는다.

## 9. hold 3건을 G5와 분리한 판단

`2025_2회_60`, `2025_3회_79`, `2026_1회_67`은 그림(권선도·블록선도·회로도)을 봐야만
풀리는 figure-dependent 문항이다. 이 3건의 answer-locked 재생성 해설은 그림 없이
작성되어, q.answer를 역산해 "제시된 그림처럼 ~이므로"라고 그림 구조를 단정했다.

G5에 이 3건을 넣으면, 검증이 "정답 역산으로 만든 해설"을 통과시키게 된다. 그건
검증의 의미를 무너뜨린다. 그래서 R8 정책에 따라 3건을 G5 적용 대상(74건)에서
빼고 별도 트랙(T3.5-K)으로 분리했다. G5는 "적용된 74건"의 게이트이고, hold 3건은
"그림 자산 확보 후 별도로 다룰 대상"으로 경계를 그었다. 게이트의 범위를 명확히
하는 것이 게이트를 신뢰 가능하게 만든다.

## 10. H1 crop 자산 확보를 먼저 한 판단

hold 3건을 풀려면 결국 그림이 필요하다. 그림을 얻는 방법은 두 가지였다 — AI 합성
`figure_svg`/`solution_svg`를 쓰거나, 원본 PDF에서 crop하거나.

AI 합성물은 헌법상 정답·원문 근거로 쓸 수 없다. 그러면 남는 건 원본 crop이고,
원본 CBT PDF가 repo에 있으니 PyMuPDF로 API 없이 확보 가능하다. 그래서 *해설
재생성보다 그림 확보를 먼저* 했다. 순서의 이유: 재생성(H2)은 비싸고(멀티모달 API)
승인이 필요한데, 그 입력인 crop은 싸고 무 API다. 싸고 확실한 선행 자산을 먼저
확보해 두면, 비싼 단계의 의사결정이 더 명확해진다 — "그림은 이미 있다, 이제
재생성할지만 정하면 된다".

## 11. hold 3건별 현재 판단

### 2025_2회_60 — 직류기 전기자 권선도

old 해설(220자)은 환상권/고상권 개념을 설명하지만, "이 그림이 왜 환상권인가"의
식별 논거가 약하다. 정답(환상권)은 답안표로 확정돼 있으나, 해설이 그 결론을
그림으로 잇지 못한다. 그래서 *재생성 후보*로 분류했다 — old 유지로 hold를 풀기엔
근거가 부족하다. 이번 cycle은 원본 crop 표시 + old 해설 유지로 처리하고, 본격
재생성은 H2(API)로 미뤘다.

### 2025_3회_79 — 블록선도 4개 비교

old 해설이 무실체다 — "블록선도 출력 × × × × ×". 게다가 이 무실체 문자열이
placeholder 정규식에 안 걸려 앱에서 'meaningful'로 오분류돼 그대로 노출되고
있었다. old 유지가 불가능한 유일한 항목이다. 그래서 *재생성 필수*로 분류하되,
이번 cycle은 무 API 원칙이라 재생성 대신 "원본 crop 표시 + 풀이 재작성 보류"
상태로 처리했다. 즉 이 문항은 "완전 해설 완료"가 아니라 "그림은 보이되 풀이는
보류"임을 명시적으로 표시했다.

### 2026_1회_67 — 게이트 회로도

old 해설(143자)은 "A·B·C 동시 입력 시 Tr 동작 → Z 소멸 → NAND"로 회로 동작
논리에 실체가 있다. 3건 중 유일하게 old 해설이 정답을 제대로 설명한다. 그래서
*old 유지 해제의 강한 후보*로 분류했다. 다만 강한 후보라고 즉시 hold를 풀지는
않았다 — clean Chrome 검증과 decision log 기록이라는 절차를 거치기 전의 해제는
절차 생략이기 때문이다. 이번 cycle은 crop 표시 + old 해설 유지까지만.

## 12. data/pdf_pages/index.json 추적 여부가 아직 미결정인 이유

crop을 앱에 연결하려면 앱이 그 경로를 알아야 한다. 앱의 그림 참조 메커니즘은
`pdfPageIndex`(= `data/pdf_pages/index.json`)인데, 이 파일이 repo에서 *미추적*
이다. 여기서 결정이 막혔다.

`index.json`을 통째 추적하면: 133KB, 193 key 중 190개가 이번 트랙과 무관하고,
이 manifest가 가리키는 이미지 1,222개는 거의 전부 미추적이다 — 즉 manifest만
추적해도 참조 대상이 git에 없어 재현성이 실제로는 확보되지 않는다. 무관한
대량 데이터를 끌어들이면서 정작 목적(재현성)은 못 이룬다.

그래서 세 안(A: 통째 추적 / B: 소형 manifest 신설 / C: app 상수)을 두고 C를
추천했지만, 이건 *재현성 위험을 어디까지 감수할지*에 대한 정책 판단이라 감독자
몫으로 남겼다. 미결정인 이유는 정보가 부족해서가 아니라, 이게 기술 선택이 아니라
*repo 추적 정책*의 문제이기 때문이다. 판단 주체가 다르다.

## 13. 왜 이 판단 로그를 데이터화하면 가치가 커지는가

판단 근거가 산문으로만 있으면 한 번 읽고 끝이다. 그러나 같은 내용을 구조화된
레코드(situation / decision / rationale / rejected_alternatives / ...)로 만들면,
다음 세 가지가 가능해진다.

첫째, **검색**. "캐시 관련 판단을 과거에 어떻게 했지"를 `topic`·`scope`로 질의할
수 있다. 둘째, **재사용**. 비슷한 상황이 오면 과거 레코드의 `rejected_alternatives`
가 "이건 이미 따져보고 버렸다"를 알려준다 — 같은 고민을 반복하지 않는다. 셋째,
**패턴 분석**. 레코드가 쌓이면 "우리는 어떤 종류의 판단을 자주 미루는가",
"기각한 대안에 공통점이 있는가" 같은 메타 분석이 가능해진다.

산문은 사람이 읽고, 데이터는 기계가 읽는다. 둘 다 있어야 판단의 자산화가 된다.

## 14. 향후 JSONL decision dataset으로 확장하는 아이디어

- **cycle별 JSONL 누적**: cycle마다 `decision_records/{cycle}_decisions.jsonl`을
  생성하고, 전체를 합치면 프로젝트 전 기간의 decision dataset이 된다.
- **스키마 고정**: `id / date / topic / scope / situation / decision / rationale /
  alternatives / rejected_alternatives / risks / status / related_commits /
  next_actions` 13필드를 안정 스키마로 유지하면 cycle 간 비교가 된다.
- **status 생애주기**: `open → fixed → closed`, 또는 `pending → done`처럼 상태
  전이를 추적하면, "DR-T35-12(index.json 추적)는 언제 닫혔는가"를 쫓을 수 있다.
- **commit 역인덱스**: `related_commits`로 "이 commit은 어떤 판단의 산물인가"를
  역추적할 수 있다.
- **생성 자동화**: `scripts/generate_supervisor_log.py`의 시드를 cycle마다 갱신해
  산문 MD와 JSONL을 함께 렌더 — 사람용·기계용을 한 소스에서 동기 생성.
- **장기 아이디어**: 레코드가 충분히 쌓이면 "비슷한 상황에서 과거 우리의 판단"을
